# Team & organizational leadership cheatsheet

A one-page reference for conflict resolution, retention, and coaching. For

<div class="cheat-sheet cheat-sheet--mba">

<div class="cheat-card">

#### Handling underperformance

Diagnose before you act: skill gap, will/motivation problem, unclear
expectations, or situational/personal issue — each needs a different fix.

</div>

<div class="cheat-card">

#### Navigating inter-team friction

Recurring friction is almost always a structural problem (unclear
ownership, misaligned incentives, competing priorities) wearing a personal
costume.

</div>

<div class="cheat-card">

#### Resolving architectural deadlocks

Most deadlocks are stuck because decision criteria were never made
explicit — not because the technical options are genuinely equal.

</div>

<div class="cheat-card">

#### Reducing developer attrition

Regretted attrition is driven by a small set of addressable causes: unclear
growth, a bad manager relationship, lack of autonomy, comp falling behind
market, and burnout.

</div>

<div class="cheat-card">

#### Building career progression frameworks

Define each level along a few consistent dimensions (scope, technical
depth, mentorship, communication) with observable, behavioral criteria —
not vague adjectives.

</div>

<div class="cheat-card">

#### Crafting tech interview loops

Design each stage to test one clear signal relevant to on-the-job success.
Common loop: recruiter screen → technical screen (baseline ability) →
onsite (system design, collaborative coding, behavioral).

</div>

<div class="cheat-card">

#### Running 1-on-1s

The 1-on-1 belongs to the engineer, not you — they set the agenda more
often than you do.

</div>

<div class="cheat-card">

#### Managing performance reviews

A good performance review contains zero surprises — every point should
already have surfaced in a prior 1-on-1.

</div>

<div class="cheat-card">

#### Adapting communication tone by audience

The same message needs a different shape for each audience — confident and
simple for sales, detailed and caveated for engineering, impact-first for
execs.

</div>

<div class="cheat-card">

#### Delegating by seniority

Delegate based on the engineer's competence and confidence for *this
specific task*, not their title.

</div>

</div>

<Exercises>
<Exercises.Task title="Diagnose four symptoms before acting" level="beginner">

For each engineer, decide whether the cause is a skill gap, a motivation problem, unclear expectations, or a situational or personal issue, and name a different first action for each:

1. Newly moved to Kubernetes work, and their pull requests need heavy rework.
2. Capable and previously strong, but output has dropped since two of their projects were cancelled.
3. Delivers work that is good but not what was asked for.
4. Sudden drop in output after a family emergency.

**Done when:** you assign skill gap, motivation, unclear expectations, and situational in that order, and each first action differs, such as coaching, a conversation about the cancelled work, rewriting the expectation, and offering flexibility.

</Exercises.Task>
<Exercises.Task title="Write a career-ladder level with observable criteria" level="intermediate">

Write the Senior level for the mentorship dimension of an engineering career ladder, using behaviours someone could actually verify.

**Done when:** you have three criteria, each observable from real evidence such as reviews given, people onboarded, or documents written, and none uses vague words like strong, good, or excellent.

</Exercises.Task>

<CaseStudy title="The one-on-one that became a status meeting">
<CaseStudy.Context>

*Illustrative scenario.* A manager uses each weekly one-on-one to go through the engineer's tickets and open pull requests.

</CaseStudy.Context>
<CaseStudy.WhatHappened>

The meeting became a status report the manager could have read on a board. The engineer stopped raising concerns about workload, growth, and the team, because there was never room for them. Months later they announced they were leaving, citing exactly the things nobody had discussed.

</CaseStudy.WhatHappened>
<CaseStudy.Lesson>

The one-on-one belongs to the engineer, and they should set the agenda more often than you do. Keep status in the tools, and use the time for what only a conversation can surface: growth, blockers, and how they are actually doing.

</CaseStudy.Lesson>
</CaseStudy>

<AISpark>

- Ask an assistant to draft a set of open one-on-one questions, then keep only the ones that invite the engineer to steer the conversation.
- Have it rewrite a vague level description into observable behaviours, and check that each one could be verified from real work.
- Ask it to design an interview loop where each stage tests exactly one signal, and confirm no two stages test the same thing.

</AISpark>
